# CMAMS V1 Design

## Purpose and scope

Build a working online-only Church Member and Attendance Management System for Grace Arena Mega Youth Church, guided by `CMAMS_Weekly_Architecture.md` (weeks 1–7). The system must support a Sunday service from registration through card issuance, scanning, supervision, and pastoral reporting. One person has one profile across lifecycle stages; each check-in has its own immutable time and demographic snapshot. Target throughput is 1,500 arrivals in 20 minutes, subject to a measured load test rather than an unverified promise.

V2 self-service, retention automation, and advanced assimilation views and V3 offline reconciliation and multi-campus rollups are excluded. The schema may include reference entities needed by V1, but the UI will not claim excluded capabilities. Never ship fabricated member data as production records.

## Architecture and interface

Use `satnaing/shadcn-admin` (MIT; retain license and attribution) as the actual frontend base: React 19, TypeScript, Vite, Tailwind, shadcn/ui, TanStack Router/Query. Remove example pages, mock API and partial Clerk auth from the shipped experience. Adapt its responsive sidebar, forms, tables and light/dark tokens. Sky blue is the primary accent, with deep navy navigation, cool neutral surfaces and restrained semantic success/warning/error colors. Prioritize a high-contrast, thumb-friendly scanner and a dense but readable desktop dashboard; do not use decorative charts without actual data.

Routes: `/login`, `/dashboard`, `/directory`, `/desk`, `/scan`, `/services`, `/cards`, `/reports`. Route navigation hides unauthorized actions, but server-side checks are authoritative. Show actionable loading, empty, denied and failure states. Never expose full PII in browser logs or public bundles.

Host the Vite frontend and `/api/v1/*` Node/TypeScript serverless handlers in the **existing** Vercel project. API modules own auth, RBAC, people and duplicate search, cards, services, check-in, reports and audit writes; a shared domain/validation module contains contracts. Use a server-side Supabase service-role connection only; no browser Supabase service key or direct database access. Keep secrets in Vercel project environment variables and document their names in `.env.example` without values. Vercel serverless compatibility and Node version are verified by build and deployment checks.

## Data and security

Apply a reviewed SQL migration for `campuses`, reference tables, `staff_users`, `people`, `households`, `person_stage_history`, `person_departments`, `qr_cards`, `services`, `attendance_records` and `audit_logs`. Enable RLS without direct browser policies. Enforce unique `(service_id, person_id)`, unique idempotency key and the partial index for one active card per person. Audit logs must be append-only. Service and person foreign keys preserve check-in history. Snapshot stage, compound and course on attendance; phone is non-unique. Use `pg_trgm` for duplicate suggestions, including swapped-name comparison; an operator must explicitly choose an existing person or confirm a distinct household member.

Staff authenticate with a salted modern password hash and a signed, HttpOnly, Secure, SameSite session cookie. Provide login, logout and session validation; no public registration. Provision the first admin with a one-time documented bootstrap command using secure input and no committed credentials. Validate request bodies, query parameters and transitions server-side. Protect cookie-authenticated mutations against cross-site requests via same-site cookie policy plus origin/CSRF validation. Restrict queries to the authenticated staff campus. Mask phone on ordinary directory results and allow unmasked absentee contact exports only for authorized, audited roles. Never send password hashes, raw QR tokens, or full audit-state PII to unauthorized clients.

Generate a random opaque QR credential, store only its SHA-256 digest, and provide a unique Crockford shortcode. Server-side token resolution is authoritative; any embedded client-side check is only a junk-code filter, never a trust boundary. The raw token may appear on a generated member card but must not be stored in the database or logged. Issuance, revocation and reissue are supervised actions; reissue invalidates the old card. Card PNG and printable PDF generation is available to authorized staff; sensitive assets must not be published to a public storage bucket. Do not promise later self-service retrieval of the raw token from its digest.

The check-in operation verifies staff role and campus, service window/status, active card and active person, then inserts atomically. Two concurrent scans of one person produce one row; repeated idempotency keys return a stable outcome and never crash a queue. A manual check-in requires a reason of at least three characters and an audit entry. An API response distinguishes success, already checked in, revoked/unknown card, closed service and permission/network errors without exposing private details. Offline capture is not supported in V1; network failures must never be shown as successful check-ins.

## Operational flows

* Desk: register with informed consent and optional phone; show scored duplicate suggestions and allow explicit household sharing; issue/download the member credential. A new person can be checked into the open service from the desk.
* Scanner: select an active service; scan with camera where available, or type a shortcode. Keep camera warm; throttle repeated reads for three seconds; show clear color **and text** status and optional audible/haptic feedback. Stop camera on route leave and support camera-denied/unsupported states. Hardware keyboard wedge entry is supported when distinguishable from ordinary typing.
* Supervisor: schedule, open and close service check-in; freeze the eligible member denominator at close; revoke and reissue cards. Reject invalid state transitions.
* Dashboard and reports: poll an authenticated summary endpoint at a short interval while visible (not direct browser Realtime); show counts by stage, active member turnout, attendance CSV and three-Sunday absentee list. Eligible members are registered before service opens. Export only authorized columns and audit sensitive exports. Department/compound reports are limited to V1 snapshot data; temporal membership analysis can follow in V2.

## Validation and release

Unit and API tests cover role-by-endpoint access, field masking, duplicate names/shared phones, service transitions, card revocation, SQL constraints, simultaneous and repeated check-ins, consent, manual audit and report denominators. Browser tests cover login, desk, scanner fallback, dashboard/error states and mobile layout. Run lint, typecheck, build, SQL migration/constraint checks and a reproducible check-in load test against a provisioned non-production environment. A failing check is reported, not concealed.
